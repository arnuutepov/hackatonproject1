# Организационный вход и публичное развёртывание · 0.10.0

## Фактический статус

Подготовлены OIDC-адаптер, MFA-проверки подписанных claims, контейнер приложения,
Caddy, oauth2-proxy, CI и политика защиты main. На 31.10.2026 реальный IdP, домен
и сервер владельцем не предоставлены. Организационный вход и публичный TLS
не активированы. Аккаунт GitHub имеет push, но не admin; защита main не изменена.

## 1. Настройка IdP владельцем организации

Используйте существующий организационный OIDC-провайдер. В его панели создайте
confidential web client с authorization code flow и PKCE S256. Единственный callback:
`https://ВАШ_ДОМЕН/oauth2/callback`. Wildcard callback не используйте.

Включите обязательную MFA для всех групп операторов, включая администраторов;
предпочтительны аппаратные ключи/passkeys. Регистрацию факторов и восстановление
доступа выполняют сотрудники и администратор IdP, а не этот репозиторий.
Запрос `acr_values` сам по себе не включает MFA на стороне провайдера.

В подписанный RS256 ID token должны попадать issuer, audience, subject, exp, iat,
auth_time и список groups. Если есть email, нужен email_verified=true. Для доказательства
MFA требуется amr со значением mfa либо конкретный acr, который IdP выдаёт только
после MFA. Сверьте это с документацией и реальной политикой именно вашего IdP.
Не добавляйте обычный password-only acr в разрешённые значения.

Создайте отдельные группы agent/lead/admin; внесите точные имена в
OIDC_ALLOWED_GROUPS и JSON OIDC_GROUP_ROLES. Например, вымышленные группы:
`{"support-agents":"agent","support-leads":"lead","support-admins":"admin"}`.
При нескольких группах выбирается старшая роль. Пользователь без разрешённой группы
не допускается. Получите issuer, HTTPS JWKS endpoint и client ID; client secret
сохраните локально в файл, не отправляйте в чат и Git.

Приложение повторно проверяет подпись, issuer/audience/azp, время токена и MFA.
Максимальный возраст iat — 15 минут, auth_time — 8 часов; токен с устаревшим
входом требует повторной аутентификации. Разрешён только RS256. Провайдеры с иным
алгоритмом или иной схемой claims требуют отдельной адаптации и тестов.
В режиме oidc вход по локальному паролю и управление локальными аккаунтами закрыты.

## 2. Сервер, DNS, секреты и запуск

Нужен Linux-сервер с Docker Engine/Compose, доступными снаружи TCP 80/443 и DNS
A/AAAA на этот сервер. Удалите ошибочную AAAA, если IPv6 не обслуживается.
Приложение и oauth2-proxy не публикуют host-порты. Подсеть 172.30.67.0/24 не должна
пересекаться с сетью сервера. При её смене синхронно измените trusted proxy CIDR.

Скопируйте deploy/settings.env.example в защищённую папку вне Git и заполните все
значения. HANDOUT_DIR — абсолютный путь к локальным rules.json и taxonomy.json.
OIDC_MFA_ACRS — JSON-массив реальных MFA assurance значений провайдера;
OIDC_ACR_VALUES — запрашиваемые у него значения. Значения не универсальны.

Владелец создаёт два файла секретов: client secret от IdP и отдельный cookie secret
ровно 32 случайных сырых байта. Не используйте демонстрационные секреты. Compose
file secrets могут сохранять права исходного файла: обеспечьте чтение для UID
контейнера, сохранив секреты в закрытой родительской папке (0700). Предпочтителен
секрет-менеджер среды. Не помещайте секреты в settings.env, образы и логи.

Из корня проекта, заменив абсолютный путь на свой:

```bash
python3 tools/deploy_preflight.py /защищённая/папка/settings.env
docker compose --env-file /защищённая/папка/settings.env -f deploy/compose.yml config --quiet
docker compose --env-file /защищённая/папка/settings.env -f deploy/compose.yml up -d --build
```

Preflight проверяет локальные предпосылки; он не доказывает корректность DNS,
MFA-политики и доступности сервера. Caddy получает и обновляет сертификат после
правильной настройки DNS и внешней доступности; реальный сертификат здесь не выпускался.
Сохраняйте тома caddy_data и app_state; настройте закрытые резервные копии и проверку
восстановления. SQLite содержит обращения и историю доступа.

## 3. Приёмка на реальном стенде

Проверьте HTTPS без предупреждений и HTTP→HTTPS, затем вход сотрудника с MFA,
отказ без группы, отказ password-only токена, разграничение agent/lead/admin,
отзыв доступа в IdP и срок действия сессии. Убедитесь, что порт 8000/4180 не открыт
снаружи и подставные Authorization/X-Forwarded-* не дают доступ.

Logout очищает сессию oauth2-proxy, но не завершает глобальную сессию IdP.
Глобальный отзыв и экстренное отключение выполняются в IdP; кешированный JWT
может оставаться действительным в пределах установленных временных ограничений.
Это не мгновенная проверка отзыва на каждый запрос.

Подписанный игровой ingress проходит отдельно от SSO, по HMAC. В compose ключи
игры не заданы: настоящий игровой вход остаётся закрытым до отдельного безопасного
подключения. Реального сервера Grand Mobile конфигурация не подключает.

## 4. Защита main — выполняет администратор GitHub

Сначала должен успешно выполниться workflow security.yml. Первый запуск GitHub
[41183280044](https://github.com/BAITC-Hacks/hack-a4a36997-oguzki/actions/runs/41183280044)
не начал ни одного шага: GitHub сообщил о проблеме оплаты либо spending limit.
Владелец должен проверить Billing & plans и повторить запуск; это не падение тестов. Он не требует справочников
организаторов и секретов: 47 проверок доступа/SSO/конфигурации, Bandit, pip-audit,
аудит репозитория. Полный make check запускается локально с приватными справочниками.

```bash
python3 tools/protect_main.py          # просмотр точной политики
python3 tools/protect_main.py --apply  # только аккаунт с admin
```

Политика требует security-gate на актуальной ветке, одобрение другого участника,
сбрасывает устаревшие одобрения, запрещает автору последнего push одобрить его,
применяется к администраторам, требует закрыть обсуждения и линейную историю,
запрещает force-push и удаление main. Скрипт проверяет admin до изменения и читает
результат обратно. Не отключайте проверки ради слияния. Для частного репозитория
доступность защиты также зависит от тарифа GitHub владельца.

Источники: [oauth2-proxy](https://oauth2-proxy.github.io/oauth2-proxy/configuration/overview/),
[Caddy HTTPS](https://caddyserver.com/docs/automatic-https),
[GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
