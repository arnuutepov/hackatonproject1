## Замеры

Windows 11, Python 3.13, 2000 блоков, Ed25519, включён антивирус реального времени.
На Linux не замерялось. Цель спецификации «append в микросекундах» выполняется только
для вычислений, а не для записи на диск.

| Шаг | p50 | p95 |
|---|---|---|
| Хеш и подпись блока | 60 мкс | 71 мкс |
| Запись в открытой транзакции | 1,35 мс | 1,54 мс |
| Commit SQLite | 3,2 мс | 3,7 мс |
| Публикация в зеркало | 3,9 мс | 4,3 мс |

В среднем на блок уходит 8,7 мс. Проверка идёт со скоростью около 5300 блоков/с.

`/triage` по настоящему HTTP, 300 последовательных запросов, две серии на каждую сборку:

| Сборка | p50 | p95 |
|---|---|---|
| Без цепочки | 3,4–3,5 мс | 17,7–18,0 мс |
| С цепочкой | 17,2 мс | 33,8–34,1 мс |

Прирост p95 составляет около 16 мс при лимите проекта 5000 мс. Эти числа нельзя сравнивать
с 4,76 мс из README: там Linux и настоящие справочники, здесь Windows и синтетические.
После сдачи пересчитайте `make benchmark` на настоящих данных.

## Отступления от постановки

- `threading.Lock` заменён на `BEGIN IMMEDIATE`: так порядок держится и между процессами,
  а вложенный замок мог бы дать взаимоблокировку.
- `operator.*` не атомарны с действием: у операторов своя база. Блок пишется до её commit.
- `triage.completed` пишет не `service.triage`, а вызывающий код: иначе в журнал попали бы
  `make predict` и оценки, а транзакция обращения потеряла бы атомарность.
- `escalation.human` строится из результата разбора, поскольку `safety.py` остаётся чистой функцией.
- sha256 вложений не считается: байтов файла в системе нет.
- Добавлены `operator.password_reset`, параметр `before` в `/audit/blocks`, `verify --export`,
  `verify --expect`.
