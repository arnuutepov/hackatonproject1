# Аудит-цепочка

> Обновление 0.11.0: исходная Wave 8 принята из пользовательского архива и проверена на Linux.
> Административные события теперь публикуются через транзакционный outbox после commit,
> с идемпотентностью и наблюдаемым pending. Описанное ниже поведение старой версии
> и Windows-замеры сохранены как история; текущий статус — в [submission-quality.md](submission-quality.md).

Подписанная хеш-цепочка аудита (append-only ledger) с внешними якорями. Каждое
значимое действие записывается отдельным подписанным блоком, и каждый блок ссылается
на хеш предыдущего. Попытка подменить прошлое ломает цепочку от точки правки до головы.

Это tamper-evidence на одной ноде, а не блокчейн в смысле консенсуса. Изменить данные
тот, кто контролирует сервер, может. Сделать это незаметно он не может, пока у него нет
ключа подписи и пока существует внешняя копия: зеркало, якорь или строка в Git.

## Что лежит в блоке

```python
@dataclass(frozen=True)
class Block:
    index: int          # 0 = genesis
    created_at: str     # ISO 8601 UTC; порядок задаёт index, а не время
    prev_hash: str      # "0"*64 для genesis
    event_type: str
    actor: str          # id оператора, game:<key>, local_cli, service или system
    payload_json: str   # канонический JSON события
    payload_digest: str # sha256(payload_json)
    block_hash: str     # sha256 канонического заголовка
    signature: str      # Ed25519(block_hash) или HMAC-SHA256
```

Канонизация: `json.dumps(event, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`.
`ensure_ascii=False` обязателен: в событиях встречается RU/KK/UZ.

Genesis хранит `chain_id`, версию схемы, время создания и описание ключа. Сырой текст
обращений и черновиков в цепочку не попадает, только дайджесты. Доказательство работает
в обратную сторону: показываем текст, считаем `content_hash`, сравниваем с блоком #N.

| event_type | Откуда пишется | Что в payload |
|---|---|---|
| `triage.completed` | `operator_store._analyze`, `service.record_triage` | вид, язык, категория, приоритет, эскалация, ID пунктов правил, `content_hash`, `draft_hash`, заявленное число вложений |
| `draft.sent` | `operator_store.mock_action` | UUID действия, `draft_hash`, ID игрока, сервер, канал, `delivered: false` |
| `escalation.human` | те же места плюс `decide` | флаги и причины из `safety.py` либо `source: operator` и `note_hash` |
| `operator.login`, `.logout` | `auth_store.py` | id, роль |
| `operator.created`, `.role_change`, `.password_reset` | `auth_store.py` | id, роль, прежние роль и активность |
| `game.event.accepted` | `operator_store.ingest`, `game_message` | UUID события и его хеш |
| `key.rotated` | `chain_cli rotate` | описание нового ключа; блок подписан старым |
| `chain.restored` | `chain_cli restored` | высота восстановления, потерянные блоки, причина |

Сохранение черновика, взятие в работу и закрытие обращения в цепочку не входят:
они остаются в таблице `events`.

## Как устроена запись

Таблица `chain_blocks` лежит в той же SQLite, что и рабочее место, поэтому действие и
его блок фиксируются одной транзакцией: откат действия откатывает и блок. Писателей
упорядочивает `BEGIN IMMEDIATE`, в том числе между процессами.

`threading.Lock` намеренно не используется: транзакция уже держит блокировку SQLite, а
второй замок рядом с ней дал бы взаимоблокировку.

Зеркало `outputs/chain-mirror.jsonl` дописывается только после commit, поэтому откат не
оставляет в нём лишних строк. Ошибка записи файла не отменяет действие: следующая
публикация допишет пропущенное. Для базы не по умолчанию зеркало и якоря лежат рядом с ней.

Журнал операторов живёт в отдельной `auth.sqlite3`, общей транзакции здесь нет. Блок
пишется до commit auth-базы: сбой цепочки откатывает действие, поэтому оно не пройдёт
без записи. Обратный случай возможен: при падении между двумя commit блок останется, а
действие нет.

`/triage` без обращения не хранит состояния, поэтому блок пишется отдельно. Если
журнал недоступен, ответ всё равно возвращается, а в лог уходит предупреждение: цепочка
записывает решения, но не определяет их. `make predict` и оценки в журнал не пишут, это
офлайн-пакеты без действий.

## Подпись

| Режим | Настройка | Кто может проверить |
|---|---|---|
| Ed25519, по умолчанию | `COPILOT_CHAIN_PRIVATE_KEY` или `COPILOT_CHAIN_KEY_FILE` | кто угодно: открытый ключ лежит в genesis |
| HMAC-SHA256 | `COPILOT_CHAIN_SIGNER=hmac`, `COPILOT_CHAIN_SECRET` | только владелец секрета |

Если ключ не задан, Ed25519-ключ создаётся рядом с базой (`chain-signing.key`). Для
локального демо этого достаточно, для развёртывания нет: ключ на том же диске, что и
база, не защищает от взлома сервера. В продакшене держите ключ вне тома с данными.

`COPILOT_CHAIN_PUBLIC_KEY` закрепляет ожидаемый ключ genesis. Без него цепочку,
пересобранную целиком под новым ключом, выдаёт только сравнение с ключом этого сервера,
а внешний проверяющий по экспорту такой подмены не увидит.

Смена ключа:

```bash
.venv/bin/python -m support_copilot.chain_cli rotate --out /secure/chain-next.key --reason "плановая"
```

Старый ключ подписывает блок `key.rotated`, в котором назван новый. Затем сервер нужно
перезапустить с новым ключом, иначе запись будет отклонена. В режиме HMAC старый секрет
переходит в `COPILOT_CHAIN_PREVIOUS_SECRETS`, иначе старые блоки станет нечем проверить.

## Проверка

`verify()` идёт от genesis к голове и останавливается на первой ошибке:

1. genesis соответствует настройкам: `chain_id`, версия схемы, закреплённый ключ;
2. `index` идёт без дыр;
3. `payload_digest` совпадает с пересчитанным;
4. `block_hash` совпадает с пересчитанным;
5. `prev_hash` равен хешу предыдущего блока;
6. подпись верна для ключа, действующего на этой высоте;
7. время не идёт назад (проверка здравого смысла, источник истины — `index`);
8. последний ключ цепочки совпадает с ключом сервера;
9. зеркало и подписанные якоря не расходятся с базой.

| Точка входа | Доступ | Ответ |
|---|---|---|
| `GET /audit/verify` | оператор | `{valid, head_hash, height, blocks_checked, first_failure, mirror, anchors}` |
| `GET /audit/blocks?limit=50&before=N` | оператор | блоки, новые сверху |
| `POST /audit/checkpoint` | admin | подписанный якорь; для сломанной цепочки 409 |

`height` — индекс головы, у пустой цепочки это `-1`. `blocks_checked` показывает, сколько блоков прошло проверку.

| Команда | Windows | Действие |
|---|---|---|
| `make chain-verify` | `./run.ps1 -Mode ChainVerify` | полная проверка, код выхода 1 при ошибке |
| `make chain-export` | `./run.ps1 -Mode ChainExport` | `outputs/chain-export.jsonl` |
| `make chain-anchor WAVE_DOC=docs/wave-8.md` | `./run.ps1 -Mode ChainAnchor` | якорь и строка для Git |
| `make chain-tamper` | `./run.ps1 -Mode ChainTamper` | демо-порча, только при `COPILOT_CHAIN_TAMPER_DEMO=1` |
| `make chain-bench` | `./run.ps1 -Mode ChainBench` | замер на временной базе |

Экспорт проверяется без базы и без закрытого ключа:

```bash
.venv/bin/python -m support_copilot.chain_cli verify --export outputs/chain-export.jsonl
```

Сверка с якорем из Git:

```bash
.venv/bin/python -m support_copilot.chain_cli verify --expect 42:<head_hash>
```

## Восстановление из бэкапа

После восстановления база короче зеркала, и проверка верно покажет `tail_truncated`.
Если это плановое восстановление, объявите его:

```bash
.venv/bin/python -m support_copilot.chain_cli restored --reason "ночной бэкап, сбой диска"
```

Появится блок `chain.restored` с числом потерянных блоков. Старое зеркало переименуется в
`chain-mirror.pre-restore-<высота>.jsonl` и останется рядом как свидетельство, а якоря
выше точки восстановления перестанут считаться расхождением. Команда отказывает, если
сама восстановленная цепочка не проходит проверку.

## Демо для жюри

Используйте отдельную базу: после порчи цепочка остаётся сломанной навсегда.

```bash
export COPILOT_OPERATOR_DB=outputs/demo/workspace.sqlite3
export COPILOT_INSECURE_LOCAL_HTTP=1
make serve
```

1. Войдите, загрузите тестовый кейс, нажмите «Отправить ответ · MOCK» и откройте
   **AUDIT CHAIN**: видны вход, разбор, эскалация и `draft.sent`. Во вкладке истории
   обращения есть ссылка «Записано в блок #N».
2. Нажмите **«Проверить целостность»**: зелёный статус и головной хеш.
3. Во втором терминале с той же `COPILOT_OPERATOR_DB`:
   ```bash
   COPILOT_CHAIN_TAMPER_DEMO=1 make chain-tamper
   ```
   Снова нажмите «Проверить»: красный статус и «Блок #N: изменены данные блока».
4. Покажите `outputs/demo/chain-mirror.jsonl` и строку якоря в `docs/wave-8.md`. Даже
   администратор сервера не перепишет прошлое незаметно.

## Обрезка хвоста

Правку старого блока цепочка ловит всегда, а тихое удаление последних N блоков сама по
себе не видит: остаток остаётся корректной цепочкой. Удаление ловится только сравнением
с внешней точкой, по нарастанию силы:

1. зеркало на диске: дешёво, но лежит на той же машине;
2. подписанный якорь из `POST /audit/checkpoint` или `make chain-anchor`;
3. head_hash в Git: `make chain-anchor WAVE_DOC=docs/wave-8.md`, затем коммит.

Roadmap, не реализовано: публикация head_hash в публичную цепочку или RFC 3161.
Публичная цепочка подходит только для якоря. Жалобы и профили игроков — персональные
данные, им там не место.

## Ограничения

- Это tamper-evidence на одной ноде, а не консенсус. Компрометация сервера вместе с
  ключом подписи позволяет переписать историю, спасает только внешний якорь или зеркало.
- Правки обнаруживаются всегда. Удаление хвоста обнаруживается при сравнении с внешним якорем.
- Если вместе с базой удалены зеркало и якоря, а внешней копии нет, потерю не увидеть.
- Цепочка — журнал, а не валидатор: на решения системы она не влияет.
- `actor` и `player_id` хранятся открыто. Зеркало и экспорт — внутренние данные;
  публиковать можно только head_hash. Короткий текст обращения можно подобрать по
  `content_hash`, если у атакующего есть зеркало, поскольку хеш не солится.
- Вложения: в MVP нет байтов файла, есть только заявленное число, поэтому sha256
  вложений пока не считается. Поле появится вместе с настоящей загрузкой файлов.
- В режиме OIDC вход происходит у провайдера, события `operator.login/.logout` не пишутся.
- Проверка полная: время растёт линейно с высотой, а запрос панели ограничен 15 секундами.
  На замеренных ~5000 блоках/с это около 75 тысяч блоков; дальше используйте CLI.
